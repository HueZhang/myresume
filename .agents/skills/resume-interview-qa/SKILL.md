# 简历模拟面试（Resume Interview QA）

## Overview

本技能把用户的简历变成面试官手里的考题来源：从简历里的真实项目、技术栈和量化指标出发，出面试官真的会问的问题，而不是泛泛的八股。面试官最在意三件事：系统是干嘛的、为什么这样设计、你是不是真的动手做过。所有题目和点评都要围绕这三点展开。

技能运行目录通常是简历仓库根目录（如 `D:\简历\myresume`），简历、题库和资料库都相对该目录定位。

## 面试轨与文件映射

按用户当前投递方向选择一条轨，只使用该轨材料，禁止混用：

| 面试轨 | 简历文件 | 题库文件 | 主资料库 |
|---|---|---|---|
| `java` | `java_resume.md` | `java_qa.md` | `reference/agent_java_offer/` |
| `csharp-backend` | `dotnet_resume.md` | `dotnet_qa.md` | `reference/dotnet-core-azure-career-path/` |
| `csharp-desktop` | `wpf_resume.md` | `wpf_qa.md` | `reference/wpf-questions/` |

通用题库（`db_interview_qa.md`、`database_project_qa.md`、`api_project_qa.md`、`high_concurrency_qa.md`）语言无关，所有轨都可以作为补充答案来源。

如果用户没说明方向，先按当前目录中的简历文件推断，或直接问用户当前面的是哪条轨。文件缺失时让用户粘贴简历内容，不要索要 JD 文件；JD 有就按 JD 定制考点，没有就按"简历内容 + 方向"推断。

## 硬性规则

- **只使用当前轨简历的内容**。投 Java 轨时不主动提 C#/WPF 经历，投 C# 后端时不提桌面端细节，投桌面端时不展开后端微服务细节。被追问到其他方向时，用"全栈基础"简短带过，不展开。
- **题目必须来自简历真实内容**：项目名、业务场景、技术栈、量化数字（如"从 1000ms 降到 200ms"）。不要出简历里没有的技术点；简历写了什么，深挖什么。
- **每条项目题都要带"为什么"**：为什么选这个方案、为什么不用另一个、代价是什么。这是简历深挖和追问的核心。
- **按轨保存产出**：错题本命名 `错题本-<track>.md`（如 `错题本-java.md`），与 `interview-strategy-summary.md` 的三轨隔离规则一致。

## 模式一：出题模式（生成题目集）

用户说"出题""生成题目"时使用。默认输出一份 markdown 题目集，包含：

1. **自我介绍**：2 分钟话术要点（开场总览 + 你最想讲的项目）。
2. **项目深挖**：简历里每个核心项目 2-3 题，覆盖：
   - 业务背景与主流程（一句话讲清楚）
   - 你负责什么、做了什么模块
   - 一个技术难点：怎么做的、为什么这么做、代价是什么
   - 预判追问 1-2 个（如"为什么不用 MQ/分布式锁/Seata？"）
3. **技术栈八股**：从该轨题库文件（`java_qa.md` / `dotnet_qa.md` / `wpf_qa.md`）和主资料库中，挑简历技术栈对应的高频题 5-10 道。
4. **场景/设计题**：1-2 道和简历业务相关（如"设计一个电子发票补偿任务"）。
5. **反问环节**：2-3 个适合问面试官的问题。

每题标注：考察点、答题要点（从题库提取标准答案）、可能的追问方向。用表格或编号列表输出，方便用户打印/背诵。

## 模式二：交互式模拟面试

用户说"模拟面试""考我"时使用。默认 30 分钟或按用户指定轮数，规则：

1. **一次只出一题**，不要一次性倒出全部题目。
2. 出题顺序：自我介绍 → 项目深挖 → 技术八股 → 场景题 → 反问。
3. 用户回答后先给**简短点评**：标记「答好 / 一般 / 没答好」并说明理由，再给标准答案要点 + 精炼的中文话术，然后出下一题。
4. 用户说"继续追问"时，就同一题再深挖 2-3 轮（trade-off、边界情况、失败案例）。
5. 结束后给总分和分项评语：表达、技术深度、项目真实性、沟通。
6. 把答得不好的题写入该轨错题本（见模式三）。

点评要克制：两三句点透问题即可，不要长篇讲课，除非用户要求展开。

## 模式三：面后复盘（错题本）

用户粘贴真实面试题时使用（不管是不是本技能出的题）：

1. 把每道题标记「答好 / 一般 / 没答好」，说明理由。
2. 对没答好的题，从该轨题库/资料库找标准答案和精炼话术。
3. 写入 `错题本-<track>.md`：新题追加，旧题更新状态；每题记录题目、考察点、我的回答、标准答案、下次必过点。
4. 最后输出 3 个下次面试前必须再过一遍的点。

如果用户同时给了面试公司/岗位，把追问集中到该公司可能深挖的方向。

## 出题与点评质量要求

- 问题要具体到简历细节（例如："你简历里写交卷用 Redis SETNX 加数据库唯一索引兜底，为什么两层都要？"），而不是"讲讲 Redis 分布式锁"这种通用题——通用题从题库出，简历题必须贴着简历。
- 点评要指出"面试官听到这个回答会怎么想"：有没有解释为什么、有没有量化结果、有没有暴露没做过。
- 涉及简历中可能被质疑的点（如"HDIS 为什么不用 MQ""Redis SETNX 和 Redisson 混用"）要主动出题，帮助用户提前统一口径，参考 `java_qa.md` 第十三节的"技术冲突与统一口径"思路。

## 示例

**出题模式输入：** "用 resume-interview-qa 按 java 方向给我出 15 道题，重点考项目深挖。"

**输出开头应类似：**

```
# Java 轨简历面试题（15 题）
## 自我介绍（2 分钟）
要点：政企平台 + 医疗信息化两条线；Spring Cloud Alibaba 全家桶；职责边界……
## 项目深挖
1. 金融保函：为什么不用 Seata/TCC？
   考察点：外部 HTTP 厂商接口不能纳入强事务；本地落库+补偿+状态机的选型逻辑
   答案要点：……  追问：补偿任务怎么保证不重复更新？
……
```

**模拟面试交互：**

> 面试官：你简历里写电子发票用 Redis SETNX 做幂等，为什么还要数据库唯一索引兜底？
> 你：（回答）
> 点评：基本答到点，但没提 Redis 重启/淘汰导致幂等标记丢失的风险。补充：……（标准答案要点）下一题：……
